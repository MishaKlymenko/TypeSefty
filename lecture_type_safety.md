# Лекція: Глибоке занурення у безпеку типів (Type Safety) у C#, Java та TypeScript

## 1. Безпека типів в сучасних мовах програмування
**Безпека типів (Type Safety)** визначається як властивість мови програмування, що гарантує неможливість виконання операцій над даними, які не відповідають їхній специфікації або внутрішній структурі. Головною метою типобезпечності є запобігання логічним та системним помилкам — таким як несанкціонований доступ до пам'яті, виклик неіснуючих методів або некоректні арифметичні операції над несумісними доменами даних.

В інженерній практиці досліджувані мови програмування реалізують різні парадигми захисту типів:

*   **Java:** Базується на строгій, статичній та номінативній системи типів. Контроль відповідності типів здійснюється дворівнево: спочатку компілятор (`javac`) на етапі збирання проєкту, а потім безпосередньо віртуальною машиною (JVM) під час виконання байт-коду.
*   **C#:** Застосовує строгу, статичну та номінативну систему типів, інтегровану у серевовище виконання Common Language Runtime (CLR). Мова чітко розмежовує типи на рівні архітектури пам'яті: значущі типи (Value Types, що розміщуються в стеку) та посилальні типи (Reference Types, що розміщуються в керованій купі).
*   **TypeScript:** Функціонує як надбудова над мовою JavaScript, реалізуючи статичну, але структурну систему типів. Головна особливість полягає в тому, що безпека типів забезпечується виключно на етапі статичного аналізу та транспайляції. У процесі генерації фінального JavaScript-коду всі типи повністю видаляються.

## 2. Архітектурна реалізація безпечності типів
Ефективність перевірки типів залежить від внутрішньої архітектури платформи, на якій виконується програмний код.

### 2.1. Механізм Type Erasure у Java
Платформа Java реалізує узагальнення (Generics) за допомогою механізму **затирання типів (Type Erasure)**. Цей підхід був впроваджений задля забезпечення зворотної сумісності з версіями Java, випущеними до появи специфікації JDK 5.

Під час компіляції інформація про параметризовані типи видаляється з байт-коду. Компілятор замінює універсальні параметри верхньою межею типу (якщо вона вказана) або базовим класом `Object`, автоматично додаючи операції явного приведення типів (casting) у місцях виклику. Відповідно, у середовищі виконання (runtime) віртуальна машина JVM оперує виключно сирими типами (Raw Types).

### 2.2. Механізм Reified Generics у C#
На відміну від Java, платформа .NET CLR підтримує **матеріалізовані узагальнення (Reified Generics)**. Інформація про типи повністю зберігається в метаданих збірки та залишається доступною під час виконання програми.

Така реалізація дозволяє розробникам виконувати динамічні перевірки типів (`typeof(T)`, `is T`) всередині узагальнених методів і класів. Крім того, CLR оптимізує роботу з пам'яттю: для кожного унікального значущого типу (наприклад, `List<int>`, `List<double>`) створюється окремий спеціалізований код, що виключає необхідність накладних витрат на пакування та розпакування (boxing/unboxing).

### 2.3. Структурна типізація у TypeScript
TypeScript використовує концепцію **структурної типізації** (еквівалент статичного Duck Typing). Сумісність типів визначається виключно їхнім вмістом та формою (структурою), а не явним оголошенням чи спадкуванням. Якщо об'єкт відповідає мінімальним структурним вимогам інтерфейсу (містить усі його властивості з відповідними типами), компілятор вважає цей об'єкт валідним. Оскільки в рантаймі TypeScript перетворюється на чистий JavaScript, будь-який захист типів після етапу компіляції повністю нівелюється.

## 3. Основні концепти типобезпечності
Для моделювання складних та безпечних систем у статично типізованих мовах використовуються механізми варіантності та захисту від відсутніх значень:

*   **Коваріантність (Covariance):** Дозволяє використовувати більш конкретний тип (похідний клас) замість базового. Зазвичай застосовується до типів, що повертаються з методів (продюсери даних).
*   **Контраваріантність (Contravariance):** Дозволяє використовувати більш загальний тип (базовий клас) замість конкретного. Зазвичай застосовується до аргументів, що передаються в методи (консьюмери даних).
*   **Інваріантність (Invariance):** Вимагає точного збігу типів. Унеможливлює використання похідних або базових типів. Більшість динамічних колекцій є інваріантними для запобігання рантайм-помилкам.
*   **Null Safety:** Набір синтаксичних та архітектурних правил мови, призначених для запобігання спробам доступу до членів об'єкта, який має значення `null` або `undefined`.

## 4. Індустріальні проблеми типобезпеки та популярні кейси
Незважаючи на переваги статичної компіляції, у реальних корпоративних системах регулярно виникають критичні проломи у безпеці типів. До найпоширеніших належать:

1.  **Помилки десеріалізації зовнішніх даних:** Проблема виникає під час конвертації JSON або XML у внутрішні об'єкти системи. Якщо структура вхідного пакета даних не збігається з очікуваною моделлю, це призводить або до негайного падіння системи, або до прихованого порушення цілісності даних (особливо актуально для TypeScript через використання типу `any`).
2.  **Помилки явного приведення типів (Downcasting):** Примусове перетворення об'єкта базового класу на дочірній без належної попередньої перевірки типу в рантаймі викликає критичні збої програми.
3.  **Неконтрольовані Null-значення:** Ігнорування розробниками перевірок на `null`, що стає причиною раптових падінь систем під навантаженням.

## 5. Практичний аналіз уразливостей систем типів та методи їх усунення

### Кейс 1: Вразливість коваріантних масивів (Java / C#)
В архітектурі Java та C# масиви історично спроєктовані як коваріантні. Це створює можливість обійти статичний контроль компілятора та спровокувати помилку під час виконання коду.

#### Проблема (Java):
```java
String[] stringArray = new String[]{"Елемент 1", "Елемент 2"};
Object[] objectArray = stringArray; // Компіляція дозволена через коваріантність масивів

// Спроба записати несумісний тип даних
objectArray[0] = Integer.valueOf(100); 
// Статична перевірка пройдена успішно, але в рантаймі відбудеться падіння:
// Exception in thread "main" java.lang.ArrayStoreException: java.lang.Integer
```

#### Вирішення (Java):
Замість масивів слід використовувати інваріантні колекції (`List<T>`), які блокують подібні операції ще на етапі компіляції.
```java
List<String> stringList = new ArrayList<>();
// List<Object> objectList = stringList; // Помилка компіляції! Типи несумісні. Захист спрацював.
```

### Кейс 2: Втрата типізації при інтеграції із зовнішніми API (TypeScript)
Під час виконання асинхронних HTTP-запитів TypeScript не може верифікувати дані, що повертаються сервером. Використання оператора примусового приведення типів `as` створює хибне враження безпеки програми.

#### Проблема (TypeScript):
```typescript
async function fetchUserProfile(userId: string) {
    const response = await fetch(`https://api.example.com/profiles/${userId}`);
    const payload = await response.json(); // payload має тип 'any'
    
    // Небезпечне припущення про структуру об'єкта
    return payload as { displayName: string; internalId: number }; 
}

const profile = await fetchUserProfile("42");
// Якщо API змінило контракт і повернуло { name: "Ivan" } замість displayName,
// наступний рядок успішно скомпілюється, але виклик помилку у клієнтському браузері:
console.log(profile.displayName.toUpperCase()); // TypeError: Cannot read properties of undefined
```

#### Вирішення (TypeScript):
Необхідно повністю відмовитися від кастингу `as` та застосовувати тип `unknown` у поєднанні з рантайм-валідаторами (наприклад, за допомогою бібліотеки *Zod*).
```typescript
import { z } from "zod";

// Визначення суворої схеми валідації в рантаймі
const UserProfileSchema = z.object({
    displayName: z.string(),
    internalId: z.number()
});

async function fetchSafeUserProfile(userId: string) {
    const response = await fetch(`https://api.example.com/profiles/${userId}`);
    const rawData = await response.json();
    
    // Валідація структури даних у рантаймі
    const validationResult = UserProfileSchema.safeParse(rawData);
    if (!validationResult.success) {
        throw new Error("Критична помилка: Невідповідність даних контракту API");
    }
    
    return validationResult.data; // Тип гарантовано валідний: { displayName: string; internalId: number }
}
```

### Кейс 3: Запобігання NullReferenceException за допомогою сучасних механізмів C#
Історично посилальні типи в C# могли приймати значення `null`, що було джерелом численних рантайм-помилок. Сучасний стандарт мови пропонує механізм Nullable Reference Types для мінімізації таких ризиків.

#### Проблема (Старий підхід C#):
```csharp
public class ClientService {
    public void RenderClient(Client client) {
        // Якщо об'єкт client або client.Address має значення null, додаток припинить роботу
        Console.WriteLine(client.Address.City); // Викликає NullReferenceException
    }
}
```

#### Вирішення (Сучасний C#):
Активація режиму `<Nullable>enable</Nullable>` у конфігурації проєкту переводить посилальні типи в категорію non-nullable за замовчуванням. Для об'єктів, які можуть бути відсутніми, розробник має явно вказати знак питання `?`, а перевірка здійснюється за допомогою механізму Pattern Matching.
```csharp
#nullable enable
public class ClientService {
    public void RenderClient(Client? client) { // Об'єкт може бути null
        // Використання безпечного навігатора та Pattern Matching
        if (client?.Address is not null) {
            Console.WriteLine(client.Address.City);
        }
        
        // Альтернативна перевірка через розширений Pattern Matching
        if (client is { Address: { City: string cityName } }) {
            Console.WriteLine(cityName);
        }
    }
}
```

## 6. Висновки та практичне застосування
Безпека типів є фундаментальним елементом розробки надійного та масштабованого програмного забезпечення. Вона мінімізує кількість помилок на етапі виконання коду та спрощує процес рефакторингу.

### Інженерний чек-ліст для розробників:
1.  **Мінімізація динамічних обхідних шляхів:** Слід уникати використання типу `any` в TypeScript, сирих типів (`Raw Types`) у Java та неперевіреного оперування типом `object` у C#.
2.  **Дворівневий захист (Компіляція + Рантайм):** Статична перевірка типів ефективна лише в межах вихідного коду системи. Усі дані, що надходять ззовні (API, бази даних, файлова система), підлягають обов'язковій валідації в рантаймі.
3.  **Експлуатація сучасних стандартів:** Необхідно тримати увімкненими опції суворого контролю компіляторів (`strict: true` у `tsconfig.json` та `<Nullable>enable</Nullable>` у `.csproj`), а в екосистемі Java замість повернення `null` використовувати контейнер `Optional<T>`.
